# Совместный просмотр YORU

## Как пользоваться

На странице аниме войти в аккаунт → «Смотреть с друзьями» → «Создать комнату». Первая версия поддерживает только управляемый источник AniLiberty. Если у него нет доступного издания, комната не создаётся. Ведущий выбирает серию после создания.

«Пригласить» выдаёт случайную ссылку комнаты: её можно скопировать и отправить в существующем чате. Зарегистрированный пользователь открывает ссылку и явно нажимает «Вступить». Ссылка даёт доступ к комнате, поэтому пересылать её следует только приглашённым. Комната не публикуется в общем списке. До8 участников, включая ведущего. Ведущий может исключить пользователя до конца жизни комнаты.

Каждый участник нажимает «Подключить плеер» — это необходимо из-за ограничений autoplay браузера. Ведущий управляет play/pause/seek/серией, гости следуют его состоянию. Качество выбирается локально, по умолчанию480p. После ухода ведущего состояние замирает через30сек с момента последнего сигнала. Можно нажать «Синхронизировать». При буферизации ведущего передаётся пауза; буферизация гостя не останавливает остальных. История сохраняется через обычный /watch не чаще30сек. Закрытие вкладки не закрывает комнату мгновенно: для этого есть «Закрыть комнату». Вернуться в свою комнату можно через ту же кнопку на странице аниме.

## Ограничения ресурсов

- `WATCH_ROOMS_MAX=3` по умолчанию, диапазон0–10. Для первого теста рекомендуется1. Значение0 выключает доступ к существующим комнатам и останавливает их клиентский опрос при следующем ответе. Переменная применяется при запуске процесса, как остальные настройки Railway.
- Один ведущий имеет не более одной активной комнаты. До3 успешных созданий/час на пользователя, до12/час на весь сайт, до4 API-попыток/час на пользователя.
- Комната живёт6часов. До8 актуальных мест и максимум32 разных допущенных аккаунта за жизнь комнаты. Место гостя освобождается после90сек без сигнала; повторный вход проверяется под блокировкой строки комнаты.
- Только текст:1000символов/сообщение, до12сообщений/минуту на пользователя. В БД и DOM остаются последние100 сообщений. Первое подключение получает последние40, затем только новые порции до40.
- Опрос состояния раз в4сек, в скрытой вкладке —15сек; при ошибках backoff до30сек. До8 участников дают примерно2 запроса состояния/сек на комнату, до6/сек для трёх полных комнат, без учёта исходного трафика сайта и команд. Каждый ответ использует несколько коротких SQL-запросов. Это ограничение нагрузки, не гарантия суммы счёта Railway.
- Ведущий отправляет сигнал раз в10сек и при командах, присутствие обновляется в БД не чаще25сек. Read/write rate limits по аккаунту защищают несколько вкладок и повторные команды.
- Видео и HLS-сегменты идут непосредственно с CDN AniLiberty. YORU не загружает, не сохраняет и не ретранслирует видео; Railway обслуживает HTML, компактное состояние, чат и кеш метаданных источника. Локальный HLS-буфер20–30сек, качество480p снижает клиентский трафик.
- Источник использует существующий `aniliberty_sources` с TTL10мин, проверкой точного Shikimori/издания, разрешений и allowlist URL. Ограничение источника после обновления кеша закрывает комнаты данного издания. Ограничения могут быть замечены с задержкой TTL; уже выданные CDN-ссылки YORU отозвать не может.
- Worker чистит истёкшие комнаты и закрытые более часа назад; создание новой комнаты также выполняет очистку, в том числе при выключенном worker. FK каскадно удаляют участников и сообщения. Снимков истории чата, файлов и отдельного медиахранилища нет.

Установить переменную в Railway перед первым тестом: `WATCH_ROOMS_MAX=1`. После публикации открыть одну комнату на двух устройствах, проверить настоящий поток, паузу/перемотку/смену серии и вкладку Usage Railway (CPU/RAM/PostgreSQL/egress). Фактические лимиты тарифа в этой задаче не были доступны. Не повышать число комнат до замера нагрузки. Платных сервисов и новых npm-зависимостей нет.

## Синхронизация и безопасность

Polling выбран для простой ограниченной нагрузки без WebSocket/Redis-сервиса. Команды доходят с задержкой до интервала опроса плюс сеть; это не покадровая синхронизация. Время ведущего экстраполируется по серверному времени, гость исправляет расхождение больше2.5сек. Блокировки браузера, скорость CDN и buffering могут требовать ручного подключения/синхронизации.

Все API требуют входа, изменения — общего CSRF. Медиа/состояние/чат доступны только действующему участнику. Ведущий проверяется сервером, version защищает от устаревших команд, точное издание/серия проверяются по источнику. Кик/блокировка/закрытие/expiry прекращают доступ. Сообщения выводятся через textContent, контакты аккаунта не раскрываются. Другие комнаты и персональные чаты не смешиваются. HTTPS сайта необходим для штатной работы браузера/копирования приглашений.

## Выпуск и проверки

Миграция020 создаёт три таблицы и строку глобальной блокировки; запускается обычным migrate при старте сервера. APK пересобирать не требуется: интерфейс загружается с сайта. Production-деплой и изменение инфраструктуры в этой задаче не выполнялись.

Модульные/HTTP тесты покрывают вместимость, stale seat, приватность, полномочия/version, позднее подключение/потерю сигнала, лимиты/очистку/повторы чата, CSRF/закрытие/кик и новые ограничения источника. Browser QA двух вкладок проверяет клиент и UI с подставным HTMLMediaElement: запуск/seek/чат/приглашение/закрытие, обе темы320/390/760/1440. Это не подтверждение настоящего декодирования HLS, воспроизведения на физическом Android или точности синхронизации реальных устройств: необходим описанный выше smoke после деплоя.
