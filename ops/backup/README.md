# Резервирование YORU

## Что настроено

- Railway service `backups`, приватный bucket `yoru-backups` (AMS), только в проекте YORU.
- Каждый день в **03:00 UTC / 06:00 Europe/Minsk**, cron `0 3 * * *`; конечный процесс, `restartPolicyType=NEVER`, без HTTP healthcheck.
- Дамп PostgreSQL custom format (`pg_dump` 18.6), все таблицы/данные, включая изображения `media`. Владелец объектов/ACL не экспортируются; секреты Railway вне базы в дамп не входят.
- После загрузки архив скачивается обратно потоком и сверяется SHA-256/размер. Только после успеха удаляются архивы `yoru/daily/` старше 14 дней. `yoru/verified-drills/` не затрагивается.
- Настройки подключения/хранилища находятся в переменных сервиса, в коде ключей нет. Web-сервису доступ к backup-bucket не добавлялся.
- Нативные volume backup schedules и ручные snapshots API отказал включить: текущему workspace требуется Pro. PITR не включён. Дамп раз в сутки оставляет окно потери до суток изменений при аварии.
- Bucket находится в том же аккаунте Railway. Локальные проверенные копии в игнорируемой `backups/` переживут удаление облачного проекта, если сохранить папку на компьютере. Потеря проекта не покрывается одними облачными копиями внутри него.

## Эксплуатация

Проверка запусков и последний журнал (из папки проекта):

```powershell
railway.cmd cron list --service backups --json
railway.cmd logs --service backups --lines 20
```

Успех: процесс завершился с кодом 0, событие `backup_uploaded_verified` содержит ключ, размер, SHA-256. Неуспех: `backup_failed`; сырой текст ошибок не выводится, поскольку ошибки DB/SDK могут содержать секреты. После исправления:

```powershell
railway.cmd cron run --service backups --yes
```

Сервис содержит SQL-пароль только в переменной `DATABASE_URL` (ссылка на Postgres) и `BACKUP_S3_*` для приватного bucket; не печатать `railway variable --json`/bucket credentials в переписку. Временная локальная копия S3 credentials находится в игнорируемой `.backup-tools/bucket.json` и нужна только для административного скачивания. Не загружать `.backup-tools/`, `.env` и `backups/` в GitHub.

Код сервиса: `ops/backup/backup.py`, Dockerfile рядом. Развёртывание:

```powershell
railway.cmd up ops/backup --path-as-root --service backups --detach
```

Расписание также выставлено явно через Railway API, поэтому после изменения сервиса сверять его Settings / Cron Schedule. Образ клиента нужно обновлять при переходе базы на новую major-версию PostgreSQL.

## Проверка восстановления

`node --env-file=.env scripts/backup-drill.js snapshot backups/name.dump` делает согласованный снимок с `pg_export_snapshot()`, сохраняет custom dump и manifest количества/хешей каждой таблицы и схемы. Требуется административное подключение к Railway PostgreSQL: утилита вызывает штатные pg_dump/pg_restore в контейнере через PostgreSQL COPY PROGRAM. Работает только как локальный административный скрипт, маршрута на сайте нет.

`node --env-file=.env scripts/backup-drill.js verify backups/name.dump` сверяет SHA-256 и восстанавливает **только в новую базу** `yoru_restore_<случайный суффикс>`. Имена генерируются и проверяются перед созданием/удалением, рабочая база не является целью. Сравнивает все таблицы, индексы, ограничения/колонки и запускает чтение страниц сайта без воркера. Временная база и файлы на сервере удаляются по окончании; локальный отчёт `*.verified.json` остаётся.

Проверенная цепочка 17.10.2026: согласованный дамп → приватный bucket → скачивание → SHA-256 → отдельная PostgreSQL база → сравнение всех данных/схемы → страницы → удаление тестовой базы. 17 таблиц, 144 тайтла, 552 серии источника, 40 тайтлов ленты, 2 изображения. Все хеши совпали. Облачный ключ проверенного снимка: `yoru/verified-drills/20261017.dump`, manifest рядом. Локальная скачанная копия: `backups/yoru-20261017-downloaded.dump`.

## Восстановление после аварии

1. Выбрать успешный архив по журналу и скачать его из приватного bucket через S3-клиент. Проверить SHA-256 по metadata/журналу; для проверенного снимка использовать manifest.
2. Создать отдельный пустой Postgres целевой версии и выполнить `pg_restore --no-owner --no-acl --exit-on-error --single-transaction` в него. Не запускать `--clean` против рабочей базы.
3. Проверить таблицы, профиль/библиотеку/историю/изображения и доступность страниц, держа `WORKER_ENABLED=false` / `AUTO_SYNC=false` на проверочном web-сервисе. Восстановленный snapshot содержит пользовательские сессии: перед реальным вводом восстановленной базы в работу удалить `sessions`, `oauth_flows`, `email_tokens`, чтобы старые сеансы и одноразовые ссылки не ожили. Не выполнять очистку в рабочей базе во время тренировки.
4. Только после проверки переключать `DATABASE_URL` web-сервиса и запускать воркер. Это отдельное решение при аварии, текущая тренировка подключение сайта не меняет. Старую базу сохранить до подтверждения результата.
5. Telegram client secret, домен, настройки источников и прочие Railway variables восстанавливаются отдельно: они не находятся в PostgreSQL-дампе.

Тесты ротации/ошибок: `python ops/backup/test_backup.py` (4 проверки). Восстановление настоящей PostgreSQL проверено дополнительно, а не заменено моками.

Дополнительно восстановлен настоящий архив ежедневного сервиса: скачивание и SHA-256 по metadata, отдельная БД, сравнение с независимым manifest согласованного снимка — все таблицы/схема совпали. Локальная копия `backups/yoru-daily-verified.dump`, отчёт `.verified.json`. Доступ без авторизации к существующему объекту проверен: HTTP 403. Запуск через движок cron завершён EXITED за 6 секунд с `backup_uploaded_verified`.
